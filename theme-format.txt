================================================================================
THEME.JSON - FORMAT REFERENCE
================================================================================

theme.json is the portfolio's colour system and its fixed display copy. It is
served as its own endpoint, separately from main.json, and the front-end fetches
it at startup. Editing a colour here re-skins the site with no code change;
editing a string re-voices it.

The file has three kinds of sections:

  tokens          - named colours, mirrored into CSS custom properties and read
                    by the entire stylesheet
  data sections   - colours that are indexed by position or keyed by a name,
                    read by the front-end's palette helpers
  strings         - the wording the site prints that is not somebody's
                    portfolio data: kickers, titles, intros, closing lines

Colour values are CSS colours. Six-digit hex is the convention. Eight-digit hex
(#rrggbbaa) is accepted where a baked-in transparency is wanted.

Nothing in this file controls layout, spacing, blur radii or shadow geometry -
only which colour is used and which words are printed. Opacity levels for
shadows and glass fills are derived in the front-end from the tokens below, so
they follow along automatically and need no entries of their own.

Omitting a key is not an error. Anything left out keeps the front-end's
placeholder, which is also what the site shows while the request is in flight.


================================================================================
TOP-LEVEL KEYS
================================================================================

version
    Schema version of this document. Bump it if the shape of the file ever
    changes, so a front-end can tell which contract it is reading.

name
    Human label for the theme. Not rendered; it exists so several theme files
    can be told apart.

description
    Free-text note about the theme. Not rendered.

tokens
    Object of named colours. See TOKENS below.

skill_palette
    Array. See DATA SECTIONS below.

domain_colors
    Object. See DATA SECTIONS below.

domain_fallback_palette_indices
    Array of integers. See DATA SECTIONS below.

default_accent
    Single value. See DATA SECTIONS below.

project_covers
    Array of arrays. See DATA SECTIONS below.

achievement_crests
    Array of arrays. See DATA SECTIONS below.

certificate_crests
    Array of arrays. See DATA SECTIONS below.

article_accents
    Array of colours. See DATA SECTIONS below.

certificates_preview_count
    Integer. How many certificates the home-page preview grid shows before it
    defers to the archive route. -1 shows the whole set, which also drops the
    "show more" link - there would be nothing behind it. Missing or invalid
    falls back to 3.

dark_fade_ms
    Integer. How long the Beyond Work route spends crossfading between the light
    and dark surfaces, in milliseconds, in each direction. The route defers its
    navigation by the same amount, so the light theme is back before the next
    page renders. Missing or invalid falls back to 500.

strings
    Object of display copy, grouped by section. See STRINGS below.


================================================================================
TOKENS
================================================================================

Each key in "tokens" becomes a CSS custom property named --color-<key> on the
document root, plus a companion --color-<key>-rgb holding the same value as
space-separated channels. The -rgb form is what lets shadows, borders and glass
fills use a token at partial opacity, so a single edit moves the solid colour
and every translucent tint derived from it together.

These tokens also back the utility classes the markup already uses (text-ink,
bg-bg, and so on), which is why renaming a key is a breaking change while
changing its value is not.

--- Text ---------------------------------------------------------------------

ink
    Primary text: body copy, headings, links. The most widely used token in the
    system. It is also the darkest stop of most gradients (primary buttons,
    badge discs, call-to-action arrows) and the tint every downward shadow is
    built from, so it carries the site's sense of depth as well as its text.

ink-2
    Second-level text: paragraphs inside cards, rendered markdown body copy,
    project and experience descriptions.

ink-3
    Third-level text: captions and secondary detail lines.

ink-4
    Faintest text: the monospaced kickers above section titles, section
    numbering, and the placeholder captions shown inside empty media wells.

on-dark
    Text that sits on a dark surface rather than on the page background. Used
    for primary button labels, the Beyond Work page's headings and body copy,
    outgoing chat bubbles, and the hobby cards.

--- Accents ------------------------------------------------------------------

accent
    The primary accent. Drives the primary button, focus rings, link hover, the
    active carousel dot, active filter chips, and the glow shadows that sit
    under all of those. The single highest-impact token in the file.

accent-2
    A companion to "accent", used where a gradient needs a lighter opening
    stop: the loading indicator, the chat launcher, and the hobby card discs.

accent-3
    Used only by the animated background wash - the blob nearest the top-left
    of the page.

teal
    The secondary accent. Appears in the hero headline gradient, the experience
    timeline spine, the Trophy Wall call-to-action arrow, and as the closing
    stop of the chat and loading gradients.

teal-2
    Used only by the animated background wash - the mid-right blob.

rose
    Used only by the animated background wash - the lower blob.

--- Backgrounds and surfaces -------------------------------------------------

bg
    The page background.

dark-bg
    The backdrop of the dark Beyond Work page, and the closing frame of the
    light-to-dark page transition.

dark-bg-2
    The raised centre of that dark page's radial backdrop, which keeps the
    surface from reading as flat.

white
    Rarely painted solid. Almost every use is at partial opacity: the highlight
    side of the neumorphic shadows, card borders, frosted navigation, and the
    lighter stop of the glass gradients. Treat it as the system's "light tint"
    rather than as a fill.

black
    The same idea in the other direction: the deep shadows on the dark hobby
    cards, media wells and badge tiles. Rarely painted solid.

surface
    The opening stop of the raised button gradient.

surface-2
    The closing stop of that same raised button gradient. Together with
    "surface" it sets how pronounced a raised control looks.

surface-3
    The closing stop of the light pill button on the Beyond Work page, which
    needs a slightly different landing than the standard raised button.

surface-sunken
    The recessed background behind the certificate archive's filter bar.

glass-2
    The cooler closing stop of every glass card gradient. Because glass cards
    are the site's dominant surface, this token shapes the overall impression
    more than its single entry suggests.

bezel-from
bezel-to
    The two stops of the pressed ring that frames achievement emblems and
    trophy badge discs. Read as a pair; inverting them turns the ring from
    recessed to raised.

tooltip
    The fill of the hover label that names an icon-only control - the social
    buttons in the hero, and anything else wrapped in the shared tooltip. Its
    arrow and its drop shadow are both derived from this one value, and the
    label's own text is drawn in "on-dark", so a light fill here needs that
    token moved with it.

select
    The text-selection highlight.

marquee-shadow
    The soft shadow cast by the scrolling skills text. Stored with a baked-in
    alpha channel (eight-digit hex), because it is a shadow tint rather than a
    surface.


================================================================================
DATA SECTIONS
================================================================================

skill_palette
    Type: array of colours.

    The rotating palette for skill chips. A skill is assigned an entry by its
    position in skills.json, not by its name or id - the first skill takes the
    first entry, and the list wraps once it runs out. Assignment happens once
    per fetch, which is what keeps a given skill the same colour on the home
    page and on every detail page.

    Consequences worth knowing:
      - To recolour one specific skill, reorder skills.json. Editing this list
        recolours the whole rotation, not one skill.
      - The length is free. Adding entries lengthens the cycle before it
        repeats; removing them shortens it.
      - Positions in this array are referenced by name elsewhere in the file
        (see domain_fallback_palette_indices), so reordering it also moves
        those fallbacks.

domain_colors
    Type: object, keyed by a domain's unique_id from domains.json.

    Fixed colours for domains. Unlike skills these are pinned rather than
    rotated, because a domain's colour carries meaning and is expected to stay
    put. Applies to domain chips and certificate accents.

domain_fallback_palette_indices
    Type: array of integers.

    The fallback for domains whose unique_id is absent from domain_colors.
    Each integer is a position in skill_palette, and unmatched domains take
    them in turn by declared order. This is why a newly added domain still
    renders sensibly without any edit to this file.

    Because the values are positions, reordering skill_palette changes what
    these resolve to.

default_accent
    Type: single colour.

    The disc colour for an achievement rendered without a crest.

    It is kept separate from the "accent" token even when the two hold the same
    value, so the emblem fallback can be tuned without moving the accent that
    the rest of the page is built on.

    (Trophy Wall badge discs take no colour from this file: each disc shows the
    badge's own display_picture from badges.json, and falls back to a hatched
    image well when that field is blank.)

project_covers
    Type: array of two-element arrays, each [from, to].

    The gradient a project card falls back to on the home rail when the project
    has no pictures in main.json. With a picture the card shows pictures[0]
    instead and none of these values are read.

    Gradients rotate by project order, the same way skill_palette does, so two
    pictureless projects listed next to each other never land on the same
    colour and a given project keeps its gradient across renders. The number of
    pairs is free; adding entries lengthens the cycle before it repeats.

    To recolour one specific project, reorder projects.json - editing a pair
    moves every project that lands on that position.

achievement_crests
    Type: array of three-element arrays, each [light, mid, deep].

    The gradients on the medal disc beside each achievement. The three entries
    are the opening, middle and closing stops of a single ramp, and the middle
    stop is placed past the centre, which is what gives the disc its domed
    look. Each ramp should therefore be three steps of one hue rather than
    three unrelated values.

    Ramps rotate by achievement order, the same way skill_palette does, so a
    list of achievements reads as a matched set instead of a repeat. The number
    of ramps is free.

certificate_crests
    Type: array of three-element arrays, each [light, mid, deep].

    The gradients on the seal disc at the top of each certificate card, on the
    home preview grid. Every card carries the same certificate mark, so the
    ramp is what tells one card from the next; as with achievement_crests the
    three entries are one hue's opening, middle and closing stops, and the
    middle stop sits past the centre to dome the disc.

    Ramps rotate by the order of certifications.json. The number of ramps is
    free; to recolour one certificate, reorder that file - editing a ramp moves
    every certificate that lands on that position.

article_accents
    Type: array of colours.

    The accent on each row of the writing index: the large ordinal, the kicker
    above the title, the rule under the ordinal and the arrow at the end of the
    row. Unlike skill_palette these are drawn as text and thin marks directly
    on the page background, so they need to be dark enough to read there - a
    colour tuned for white text on a filled chip washes out here.

    Accents rotate by the order of articles.json, so a row keeps its colour
    while the index is searched. The number of colours is free; omitting the
    key falls back to skill_palette.


================================================================================
STRINGS
================================================================================

strings
    Type: object of objects. Each inner object is one section or route, and its
    keys are the individual lines that section prints.

    What belongs here is every word the site prints that is not part of
    anyone's portfolio: the numbered kicker above a heading, the heading itself,
    the paragraph under it, the line that closes the section - and equally the
    button and link labels, the form fields, the filter and empty-state wording,
    and the accessible names on the controls. Names, blurbs, roles, project
    write-ups and hobby descriptions are content and come from main.json
    instead.

    The front-end ships no wording of its own. Anything this file does not name
    renders as strings.common.no_data, which makes the gap visible in the UI
    rather than papering over it with a default that only exists in the bundle.

    Some wording is shared by several surfaces - the way back, a reset control,
    a count. Those live once under common, and a group may override the same key
    to say something more specific: common.back_label reads "Back to portfolio"
    everywhere, while projects.back_label reads "Back to work" on that one
    route. A group that names no override inherits common's.

    A string may carry {placeholders}, which the front-end fills with values it
    supplies. This keeps the sentence in the theme rather than assuming a word
    order in the code:

      chat.sleeping_body      {name}  - the assistant's display name
      common.count_shown      {count} - how many rows survive a filter
      articles.count_one      {count} - the writing index's result count,
      articles.count_many               singular and plural

    Groups:

      common          wording shared by more than one surface, plus no_data
      hero            the hero's resume CTA
      experience      02 - the timeline section, and the kicker on a company's
                      detail route
      projects        03 - the project rail, and the kicker on a project's
                      detail route
      certificates    04 - the preview grid, plus the archive route's own
                      heading and its no-results line
      achievements    05 - the achievements list
      trophy_wall     the Trophy Wall route and the CTA that leads to it
      beyond_work     the Beyond Work route and the CTA that leads to it
      articles        08 - the writing index
      footer          the closing headline and the whole message form
      chat            the assistant panel's chrome
      status          the loading, error and not-found screens

    Keys. Every group draws from one vocabulary rather than naming its own
    lines: kicker and title are what the home page prints, and the detail_*
    set is what the route that section leads to prints.

      kicker          The mono, uppercase line above the title, on the home
                      page and on the route that section leads to. The
                      convention is "NN - Section Name".
      title           The home page section heading.
      detail_title    The heading on that route.
      detail_intro    The paragraph directly under that heading.
      detail_outro    The closing line at the foot of that route, set in the
                      display face. One thought, not a paragraph.
      empty_body      Shown when there is nothing to render - a filter that
                      matches no rows, or content that failed to load.

    A group carries only the keys it renders. experience and projects are a
    heading over a list on the home page, so they carry kicker, title and
    detail_outro - the detail route takes its heading from the job or project
    itself and opens with no framing paragraph. trophy_wall and beyond_work
    are routes in their own right: title belongs to the home page CTA, the
    detail_* set to the page, and kicker is printed on both.
    certificates adds empty_body for its filtered archive. articles is a route
    of its own: kicker and title head the writing index, detail_intro is the
    paragraph under them, and three keys cover the states where there is
    nothing to print -

      articles.empty_body         Shown when main.json carries no articles key,
                                  so the index has nothing to list.
      articles.not_found_body     Shown when a /article/<id> URL names an
                                  article the index does not have. A different
                                  situation from an empty index, so it gets its
                                  own line.
      articles.search_empty_body  Shown when the index search matches nothing.
      articles.content_empty_body Shown when an article's content URL does not
                                  answer, so there is no body to render.

    footer and status
    keep the same shape - footer.kicker is the message form's label and
    footer.title the closing headline; status.kicker is the line printed under
    the loading mark and status.empty_body the message shown when the content
    request fails without one of its own.

    The one exception:

      trophy_wall.stat_badges    Labels under the two counters at the top of
      trophy_wall.stat_platforms the Trophy Wall. They name specific counters,
                                 so no shared key covers them.

    Omitting a group, or a key inside one, is not an error, but it is visible:
    the front-end carries no default wording, so a missing string renders as
    strings.common.no_data. A group key that common also declares falls back to
    common's before it falls back to no_data.


================================================================================
NOTES
================================================================================

- Renaming a token key breaks the front-end; changing its value does not.
- Adding a key the front-end does not know about is harmless - it is ignored.
- A partial file is valid. Whatever it omits keeps the placeholder rather than
  falling back to a previous theme, so a half-written file degrades cleanly
  instead of mixing two themes together.
- theme.json is written by hand and served as-is. It is not produced by
  validate_and_combine_json.py and does not need that script run after an edit.
